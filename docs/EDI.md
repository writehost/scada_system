# SCADA EDI — электронный документооборот

Отдельное приложение экосистемы SCADA System, как YMS: свой процесс и домен, общая база `wms_edge`, общие пользователи и организации. WMS, YMS и GSMT при установке EDI не меняются.

| | |
|---|---|
| Код | `edi-app/` в этом репозитории |
| Порт | `127.0.0.1:3016` |
| Стек | Next.js 16 (App Router), TypeScript, PostgreSQL (`pg`), Tailwind 4 — тот же, что у WMS/YMS |
| Схема | таблицы `edi_*`, версионируемые миграции с checksum; `npm run ensure` |
| Файлы | хранилище по SHA-256: локальный каталог или S3-совместимое (`EDI_STORAGE`) |
| Фон | очередь в PostgreSQL, отдельный worker (`npm run worker`), один на такт через advisory lock |

Django/Celery/Redis не вводились: в экосистеме их нет, а требование — не менять стек без причины.

## 1. Аудит экосистемы (что найдено и как использовано)

| Сервис | Что есть в репозитории | Как EDI с ним работает |
|---|---|---|
| **SCADA ID** | Keycloak-реалм `id.scada25.ru/realms/scada-system-id`, OIDC code+PKCE, API прав `GET /api/v1/permissions/resolve?application=…` (`lib/wms/scada-id.ts`) | Тот же контракт с `application=scada-edi`, клиент `scada-edi`. Пользователь заводится/обновляется в `wms_users`; роли EDI хранятся отдельно (`edi_user_roles`), складские роли не трогаются. Второй базы учётных записей нет. |
| **Пользователи и организации** | `wms_users` (scrypt), `wms_roles`, `wms_sites` — арендаторы SaaS | В production — SCADA ID; пароль WMS и наследование его ролей выключены по умолчанию. Организация = `wms_sites`. Одна персона может иметь учётные записи в нескольких организациях — переключатель в шапке, доступ перепроверяется при переключении. |
| **API-токены** | персональные `wmsu_…` (`wms_user_api_tokens`) | Принимаются EDI как `Bearer` (SCADA Mobile, интеграции). Тот же токен сервисного пользователя WMS используется EDI для вызовов WMS. |
| **SCADA WMS** | HTTP API: номенклатура, `lookup` (штрихкоды), алиасы поставщиков, справочник поставщиков, заказ на приход `PUT /api/wms/receiving/inbound`, проведения приёмки `GET /api/wms/receiving/stock-posts`, уведомления | Только через HTTP API (`lib/edi/integrations/wms.ts`), без записи в таблицы WMS. Остатки EDI не меняет. |
| **SCADA Mobile** | мобильный интерфейс и ТСД внутри WMS (`app/mobile`, Capacitor) | Второе приложение не создавалось: EDI адаптивен, лента задач — `GET /api/edi/mobile/inbox` с `wmsu_`-токеном, уведомления — в колокольчик WMS. |
| **QPass** | REST `qpass.scada25.ru/api/v1/equipment/ensure` (паспорт оборудования) | Документов ТО/ремонта в API QPass нет — интеграция помечена недоступной, не имитируется. |
| **APS, YMS, EMS** | APS — внутри WMS (планы производства); YMS — визиты в общей базе без API документов; EMS — контрактов нет | Не подключены: нет опубликованных контрактов для документов. Слой `edi_external_links` готов принять ссылки, когда контракты появятся. |
| **Дизайн-система** | shadcn/ui, токены oklch (светлая/тёмная), Inter, акцент `oklch(0.83 0.18 115)` | Те же токены и шрифт, своя минимальная библиотека компонентов (как в YMS), `lucide-react`. |
| **КриптоПро** | `crypto-pro` (ЭЦП Browser plug-in) в WMS для ГИС МТ | Тот же плагин для откреплённой подписи CAdES в браузере. |

## 2. Архитектура

```
Браузер ── edi-app (Next.js) ──┬── PostgreSQL wms_edge: wms_* (чтение пользователей/организаций), edi_*
                               ├── Хранилище файлов (local | S3, ключ = SHA-256)
                               ├── SCADA WMS HTTP API (wmsu_-токен) ── опционально
                               ├── SCADA ID (OIDC + API прав) ── обязателен в production
                               ├── Сервис проверки подписи ── опционально
                               └── Операторы ЭДО (EDI Provider Gateway) ── адаптеров пока нет
```

Код (`edi-app/lib/edi/`):

| Модуль | Назначение |
|---|---|
| `schema.ts`, `seed.ts` | схема `edi_*`, реестр форматов, тарифы, системные шаблоны |
| `actor.ts`, `permissions.ts` | актор запроса, роли EDI, права; проверка на каждый запрос |
| `documents.ts`, `doc-types.ts` | реестр типов (30 видов), жизненный цикл, версии со снимком и SHA-256, ACL, нумерация, поиск |
| `journal.ts`, `detail.ts` | журнал, счётчики, главная, карточка и доступные действия |
| `parsers/xml.ts` | безопасный XML: без DOCTYPE/ENTITY, лимиты, windows-1251 |
| `parsers/upd.ts`, `parsers/table.ts` | УПД/СЧФ 5.01 и 5.03, CSV, XLSX (без сторонних библиотек) |
| `import.ts`, `files.ts`, `storage.ts` | загрузка, ZIP с лимитами, проверка типов по сигнатуре, хранилище |
| `matching.ts`, `wms-receipt.ts`, `wms-suppliers.ts` | сопоставление номенклатуры, заказ на приход, сверка факта, акт расхождений, связь с поставщиками WMS |
| `workflow.ts` | маршруты: версии, этапы, параллельные шаги, условия, сроки, эскалация, делегирование |
| `signatures.ts`, `edo.ts` | подписи CMS, проверка, шлюз операторов ЭДО |

Три независимые оси статуса документа, которые не смешиваются:
`status` — внутренний жизненный цикл; `exchange_status` — юридически значимый обмен; `wms_status` — связь со складской операцией.

## 3. Сквозной сценарий УПД → WMS → архив

1. УПД (XML ФНС, можно ZIP с `.sig`) загружается в «Загрузка». Оригинал сохраняется побайтно, SHA-256 в карточке.
2. Контрагент — по ИНН/КПП продавца; если его нет, создаётся из реквизитов файла одним действием.
3. Строки, суммы, НДС, GTIN, коды маркировки извлекаются; арифметика проверяется.
4. Сопоставление: сохранённое соответствие → GTIN (штрихкод WMS) → алиас WMS по коду поставщика → код номенклатуры → алиас по точному названию. Похожие позиции только предлагаются.
5. Замечания показываются до создания документа (несопоставленные строки, дубль, формат не применяется на дату, покупатель — не ваша организация).
6. Пользователь подтверждает; ручные сопоставления запоминаются в EDI и создаются алиасом в WMS.
7. Создаётся заказ на приход `EDI-<id>` в WMS. Остатки не меняются.
8. Склад принимает на ТСД и проводит приёмку существующей логикой WMS.
9. Фоновая сверка читает проведения WMS и сравнивает с документом построчно.
10. В EDI статус «Принято складом» или «Принято с расхождениями», уведомление ответственному, из карточки — акт расхождений.
11. Согласование по маршруту; подпись — только файлом CMS из криптографического ПО. Отправка оператору ЭДО — только при подключённом проверенном адаптере (сейчас кнопки нет).
12. Завершение, архив, выгрузка ZIP: оригиналы, подписи, квитанции, версии, история, `manifest.json` с SHA-256.

## 4. Проверка

```bash
cd edi-app
npm test                                              # 22 модульных теста
E2E_PG=postgres://postgres@127.0.0.1:5544 npm run test:e2e   # 11 сквозных тестов
npm run build
```

Сквозной тест поднимает **настоящий WMS** из корня репозитория (`next dev`) на чистой тестовой базе и проходит шаги 1–12 через реальные маршруты WMS. Минимальная схема WMS для этой базы — `edi-app/scripts/fixtures/wms-schema.sql` (полная схема WMS в репозитории не хранится). Единственный шаг, который тест делает вместо склада, — запись проведения ТСД (шаг 8) в том же формате, что пишет `finalizeReceivingSession`; EDI читает её через HTTP WMS.

Также проверено: изоляция организаций, конфиденциальные документы, права ролей, повтор загрузки, сохранённые сопоставления, делегирование, эскалация без повторных уведомлений, доставка уведомления в WMS, работа EDI при недоступной WMS, неизменность подписанной версии. Модульные тесты: XXE/сущности, windows-1251, УПД 5.01/5.03, ИНН/ОГРН, эталон подписи AWS SigV4, шифрование секретов, разбор CMS на подписи OpenSSL, ZIP-бомба, макросы в DOCX, подмена расширения.

Интерфейс пройден в Chromium (Playwright): вход, главная, загрузка и ручное сопоставление, приёмка в WMS, карточка, конструктор, тёмная тема, телефон 390 px — без ошибок в консоли.

## 5. Что не сделано или не проверено (честно)

| Тема | Состояние |
|---|---|
| **Формат УПД** | Разбор проверен на синтетических файлах, построенных по структуре 5.01/5.03. Официальная XSD и реальные файлы поставщиков из этой среды недоступны (сеть закрыта). Перед продуктивом — прогнать архив реальных УПД. Корректировочный УКД (КНД 1115133) сохраняется как файл без разбора. |
| **Исходящие XML ФНС** | Не формируются: без утверждённой XSD в реестре это была бы подмена формата. Исходящие документы — структурированные реквизиты + печатная форма + подписываемый файл версии (JSON). |
| **Операторы ЭДО** | Шлюз, журнал обмена, квитанции, идемпотентность есть; адаптеров нет — ни один оператор не проверен на тестовом контуре (нет доступов). Отправка через ЭДО и роуминг в интерфейсе не показываются. |
| **Проверка подписи ГОСТ** | Локально: разбор CMS, сертификат, срок действия на момент подписания. Криптографическая проверка — через внешний сервис (Администрирование → Интеграции); без него статус «не проверена». |
| **МЧД** | Номер МЧД сохраняется с подписью; проверка полномочий по реестру ФНС не подключена. |
| **Торговый EDI** (ORDERS, ORDRSP, DESADV, RECADV, INVOIC) | Не реализован: нужны спецификации конкретного партнёра/провайдера. EDIFACT и форматы ФНС не смешиваются. |
| **OCR** | Не подключён: PDF и изображения сохраняются, реквизиты вводятся вручную; DOCX/TXT — извлечение текста и подсказки реквизитов. |
| **APS, YMS, QPass (ТО), EMS** | Нет контрактов для документов — интеграции не включены. |
| **WebSocket** | Используется SSE (`/api/edi/events`) поверх `LISTEN/NOTIFY` — как механизм событий WMS. |
| **S3** | Подпись запросов проверена эталоном AWS; на живом хранилище не запускалось. |
| **Email** | SMTP без внешних библиотек; на реальном сервере не проверялся. |
| **Цены тарифов** | Не установлены: нужен расчёт себестоимости (оператор ЭДО, подпись, хранение). Лимиты и признаки тарифов меняет оператор платформы. |
| **Сроки хранения** | Стартовые значения по типам с основанием; сверить с учётной политикой. Удаление — только архивных документов с истёкшим сроком и решением администратора. |
| **Плитка в лаунчере WMS** | Не добавлялась, чтобы не менять WMS; адрес EDI можно добавить в `components/wms/apps-launcher.tsx` после выкладки. |

## 6. Установка

```bash
cd edi-app
cp .env.example .env            # секреты не коммитить
npm install
DATABASE_URL=… npm run ensure   # схема edi_*, справочники
npm run build
node .next/standalone/server.js # PORT=3016; .next/static и public копируются рядом, как у YMS
```

Подключение WMS: в WMS выпустить персональный токен сервисного пользователя (роль начальника склада), затем в EDI «Администрирование → Интеграции → SCADA WMS» указать адрес WMS и токен и нажать «Проверить подключение». Вход через SCADA ID: завести в реалме клиента `scada-edi` с redirect `https://<edi>/api/auth/scada-id/callback` и выдать приложению `scada-edi` гранты (`admin`, `operator`, `signer`, `approver`, `viewer`).

## 7. Роли

Роли EDI: администратор, делопроизводитель/бухгалтер, согласующий, подписант, юрист, просмотр, аудитор. В production без назначенных ролей EDI доступ запрещён. Наследование WMS возможно только при явном разрешении администратора сервера (`EDI_ALLOW_WMS_ROLE_FALLBACK=1`): `admin` → администратор EDI, `warehouse_manager` → делопроизводитель + согласующий, `warehouse_operator` → просмотр, `auditor` → аудитор. Права проверяются на сервере для каждого запроса; конфиденциальные документы видят автор, ответственный, участники маршрута, явно допущенные и роли с правом на конфиденциальное.
