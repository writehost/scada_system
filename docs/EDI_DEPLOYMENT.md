# SCADA EDI: аудит и развёртывание, 14 октября 2026

## Исходная версия и область изменений

Репозиторий: `writehost/scada_system`. Исходная ветка Claude:
`claude/inspiring-archimedes-tq865p`, коммит `45f51b818d149f1c49da635f31928832f9ca0416`.
Рабочая ветка: `codex/edi-production`. Изменения ограничены `edi-app/` и документацией.
Основные приложения WMS, YMS и GSMT не изменялись.

## Подтверждённые проблемы и исправления

- В исходных зависимостях npm обнаружил 1 critical и 2 high уязвимости. Next.js обновлён
  с 16.2.4 до 16.4.0. Повторный аудит: 0 известных уязвимостей. Обоснование обновления:
  [официальные исправления Next.js](https://vercel.com/changelog/next-js-may-2026-security-release).
- Неявное наследование административных ролей WMS и вход по паролю выключены в production.
- Переключение организации ограничено списком, который подтверждён при входе; совпадение
  логина больше не расширяет доступ. Для SCADA ID используется точный внешний идентификатор.
- Callback не выбирает организацию из клиентского параметра при отсутствии подтверждения
  SCADA ID. Автоматическое связывание существующей учётной записи по email и её повторная
  активация запрещены: конфликт требует подтверждённой связи администратором.
- Сессия SCADA ID хранит зашифрованные access/refresh tokens на сервере. API повторно
  запрашивает полномочия SCADA ID; обновление токенов сериализуется блокировкой строки.
  Выход удаляет серверную сессию. Полный выход из SSO-реалма пока не реализован.
- Добавлена проверка Origin для изменяющих запросов с cookie и ограничение тела запроса
  по реально прочитанным байтам, в том числе без Content-Length.
- Исходящие запросы интеграций в production разрешены только на явно указанные HTTPS
  origins; HTTP redirects запрещены. Список задаётся администратором сервера.
- SSE проверяет видимость документа перед передачей его ID, освобождает подписки при
  разрыве и переподключается не реже одного раза в минуту для обновления авторизации.
- Production не запускает DDL в API и не запускает worker внутри Next.js. Worker выделен
  в отдельный процесс; устранены локальное наложение тактов и сохранение advisory lock
  после ошибочной транзакции. Доставки фиксируются отдельно; webhook имеет стабильный
  Idempotency-Key. Доставка остаётся at-least-once и требует дедупликации у получателя.
- Введены миграции 1–3 с checksum, транзакцией, блокировкой и отказом при несовместимой
  схеме/откате на более старый набор миграций. Отсутствующие колонки старой схемы требуют
  отдельной явной миграции; они не считаются автоматически исправленными.
- Исходный E2E больше не удаляет существующую фиксированную базу перед запуском;
  для каждого запуска используется новое случайное имя тестовой базы.

## Мультипровайдерная архитектура

Добавлены контракты адаптеров с опциональными возможностями, независимые подключения
операторов, внешние юридические экземпляры и отдельные события обмена. Составные внешние
ключи проверяют организацию подключения и документа. Реализованы каталог операторов,
API и вкладка «Операторы ЭДО» для сохранения черновиков подключений и их отключения.

**Ни один оператор не подключён и не проверен.** Синхронизация, реальный единый журнал
внешних документов, отправка и автоматическая маршрутизация не реализованы. Черновик
настроек не означает действующее подключение. Диадок, Saby, Такском и Астрал требуют
официальных API, тестовых доступов и испытаний; фиктивных адаптеров нет.

## Проверки

- 22 исходных модульных теста: проходят; OpenSSL добавлен в PATH среды проверки.
- 5 дополнительных проверок: политика production, CSRF, redirect, SSRF, chunked body limits — проходят.
- Проверка типов и локальная production-сборка Next.js 16.4.0: успешны.
- 3 теста на настоящей отдельной PostgreSQL 16: повтор миграций, checksum/освобождение
  блокировки, несколько учётных записей одного оператора и межорганизационные FK — проходят.
  Использована минимальная тестовая схема идентичности; это не проверка актуальной WMS.
- Полные 11 исходных E2E не запускались: они используют восстановленную схему и прямую
  запись проведения приёмки. Нельзя считать их подтверждением реального процесса склада.
- Реальный вход SCADA ID, WMS, операторов ЭДО, SMTP, S3, ГОСТ и МЧД не проверен.
- Нагрузочные испытания 10 000/100 000 документов не проводились.

## Сервер и конфигурация

Сервер: `193.233.220.205`, Ubuntu 22.04.5, 1 CPU, 1.9 GiB RAM, 2 GiB swap,
около 16 GiB свободного диска на preflight. На сервере уже работают Alpaca, SCADA EMS
и token gateway. Порт 3016 занят EMS; он сохранён. EDI публикует контейнерный порт
3016 только на **127.0.0.1:3017**. Nginx в существующем контейнере обращается к EDI
по отдельному Docker DNS-имени в существующей сети `alpaca_default`.

Файлы развёртывания:

- `edi-app/Dockerfile`: Linux production-сборка, standalone, `.next/static`, `public`.
- `edi-app/deploy/compose.yaml`: отдельный контейнер с непривилегированным пользователем,
  read-only root, ограничением памяти/CPU, ротацией логов, restart и проверкой живого процесса.
- `/etc/scada-edi/runtime.env`: конфигурация вне Git, root:root, 0600; собственные случайные
  ключи сессий и шифрования. Внешние секреты и URL базы не подменены фиктивными значениями.
- `/var/lib/scada-edi/storage`: постоянное локальное хранилище.
- `edi-app/deploy/nginx.conf`: отдельный virtual host, HTTPS, SSE без буферизации,
  26 MiB предел запроса, security headers и очищенные proxy headers.
- Сертификат Let's Encrypt: `edi.scadasystem.io`, первоначальное окончание 12 января 2027.
  Обновление — `scada-edi-tls-renew.timer`, два раза в сутки, только сертификат EDI.

`/api/health` отражает готовность, а не просто наличие процесса: при отсутствии базы
или секрета SCADA ID возвращает HTTP 503 `setup_required`. Docker healthcheck проверяет
живую страницу входа; его healthy не означает готовность документооборота.

## Завершение настройки

1. Получить реальное защищённое подключение к `wms_edge`. Не использовать PostgreSQL
   EMS и не создавать копию производственной WMS. Выдать отдельные минимальные полномочия.
2. Сделать и проверить резервную копию затрагиваемых EDI-данных и согласовать миграции
   на актуальной тестовой схеме. Применить `scripts/ensure.ts` отдельным миграционным
   пользователем. Runtime не должен иметь DDL-полномочий.
3. Добавить `DATABASE_URL` и `SCADA_ID_EDI_CLIENT_SECRET` в файл конфигурации вне Git.
   Подтвердить confidential-клиент `scada-edi`, code+PKCE, callback
   `https://edi.scadasystem.io/api/auth/scada-id/callback`, гранты и organization.site_code.
4. После смены runtime.env пересоздать только контейнер EDI; затем включить профиль worker.
5. Подключить фактический WMS API и токен сервисного пользователя, включить его HTTPS origin
   в `EDI_OUTBOUND_ORIGINS`. Проверить `/api/wms/receiving/finalize` на тестовой базе через
   реальный API. Нельзя имитировать это прямой записью `receiving_stock_post`.
6. Проверить документы, import, ACL, роли, смену/отзыв полномочий, refresh, logout,
   мобильный UI и SSE с реальными тестовыми учётными записями.
7. Отдельно завершить официальные XSD/реальные УПД, криптографическую проверку, МЧД,
   provider adapters, SMTP/S3, нагрузочные проверки и коммерческую UX-полировку.

## Откат

Релизы сохраняются в `/opt/scada-edi/releases/`, образы — с отдельными тегами.
Переключение выполняется изменением `EDI_IMAGE` и `docker compose up -d edi` в каталоге
релиза. Нельзя выполнять down общей инфраструктуры. Возврат схемы путём удаления таблиц
не предусмотрен: миграции добавляющие; перед несовместимым откатом нужна отдельная проверка.
Исходный nginx конфиг сохраняется до добавления include EDI. При полном снятии первого
релиза удалить только include EDI, проверить nginx -t и сделать reload.

Настроен отдельный SSH-ключ Ed25519; вход root по нему проверен. Закрытый ключ хранится
только на локальной машине пользователя в `.ssh/scada-edi-193-233-220-205`, с ограниченным
ACL. SSH-пароль не сохранялся в коде, runtime.env или отчёте; первоначальный пароль
следует заменить.


## Фактическая публичная проверка после запуска

- https://edi.scadasystem.io открывается с доверенным TLS-сертификатом; корень переводит
  на `/login`. Страница входа, JavaScript, CSS и иконка возвращают HTTP 200.
- Браузер показывает сообщение об отсутствии настроенного SCADA ID; ошибок и предупреждений
  в консоли при загрузке не обнаружено. Полные экраны за авторизацией не проверены.
- `/api/auth/providers`: password=false, scadaId=false, database=false.
- `/api/health`: HTTP 503, `setup_required`. **Полноценный запуск документооборота не выполнен.**
- API документов без входа: HTTP 401; изменяющий запрос с посторонним Origin: HTTP 403.
- Перезапуск только контейнера EDI проверен: после старта страница входа снова HTTP 200.
- SCADA EMS после добавления EDI: страница входа HTTP 200, оба systemd-сервиса active.
- Тестовое обновление сертификата (`--dry-run`) успешно. Временная тестовая PostgreSQL
  и её отдельная сеть удалены после проверок; производственные базы не изменялись.
- Развёрнутый образ: `scada-edi:20261014-02`; текущий каталог: `/opt/scada-edi/current`.

Остаются обязательные данные: реальное защищённое подключение к `wms_edge`, секрет клиента
`scada-edi` и подтверждение callback/грантов. Без них нельзя честно подтвердить вход,
создание документов, WMS или реальный обмен с операторами ЭДО.
