# SCADA EMS — учёт и управление потреблением ресурсов

Отдельное приложение экосистемы SCADA System по образцу YMS: свой процесс и домен, общие SCADA ID, PostgreSQL и дизайн-система. WMS, YMS и GSMT не изменялись.

| | |
|---|---|
| Код приложения | `ems-app/` (Next.js 16, React 19, TypeScript, PostgreSQL) |
| Агент шлюза | `ems-gateway/` (Node.js 18+, без зависимостей) |
| Порт | `127.0.0.1:3016` (`npm start`) |
| Фоновый обработчик | `node scripts/worker.ts` (отдельная служба) |
| Миграции | `ems-app/db/migrations/*.sql`, `node scripts/migrate.ts` |

## 1. Аудит экосистемы (что переиспользовано)

| Область | Что есть в репозитории | Решение в EMS |
|---|---|---|
| Стек | Next.js 16 App Router, React 19, TS, Tailwind 4, `pg`, recharts 2.15, lucide, shadcn (new-york) | Тот же стек, без новых тяжёлых зависимостей |
| Развёртывание отдельных модулей | `yms-app/`: свой процесс, порт, standalone-сборка, общая БД | Повторено: `ems-app/`, порт 3016, `output: standalone` |
| SCADA ID | `lib/wms/scada-id.ts`: Keycloak realm `scada-system-id`, authorization code + PKCE S256, `userinfo`, `GET {api}/api/v1/permissions/resolve?application=…` (гранты по приложениям, `organization {slug,name,site_code}`, `is_super_admin`) | Тот же контракт, приложение `scada-ems` (`SCADA_ID_APPLICATION`). Отдельной системы паролей нет |
| Сессии WMS | HMAC-токен без серверного состояния, отзыв только глобально (`WMS_AUTH_REVOKED_BEFORE`) | Подписанный идентификатор строки `ems_sessions`: выход и отзыв конкретной сессии действуют сразу |
| Почта | Помощник `/usr/local/bin/wms-send-mail.py` (`WMS_SEND_MAIL_BIN`), JSON `{subject,text,html,recipients,fromName}`, отправитель support@scada25.ru | Провайдер `helper` использует его же. Поверх — очередь, повторы, журнал доставки |
| Мобильное приложение | `android/` — нативный клиент ТСД WMS; push реализован как long-poll подписки + периодическая синхронизация (WorkManager), FCM нет | Отдельного приложения и push-системы не создавалось. Для SCADA Mobile: обмен токена SCADA ID, сводка, лента с курсором и long-poll |
| Дизайн | Токены `app/globals.css` (oklch, салатовый primary, тёплый фон, `--radius: 1rem`), `.wms-panel`, плотные KPI-плитки, боковое меню с группами | Те же токены и классы (`.ems-panel`), та же структура меню и плитки |
| Модель пользователей | `wms_users` / `wms_sites`, площадка = завод | Для EMS введены организации: домашние клиенты не являются площадками WMS. Таблицы `ems_*` в той же БД, без внешних ключей на `wms_*` |

Чего в репозитории нет: кода SCADA ID и SCADA Mobile (только клиенты к ним), брокера MQTT, платёжного провайдера. Интеграции с ними реализованы по видимым в коде контрактам и проверены на тестовых двойниках; с реальными сервисами не испытывались.

## 2. Архитектура

```
Браузер / SCADA Mobile ──HTTPS──► ems-app (Next.js: страницы + REST API)
                                     │  withOrg(): транзакция с ems.org_id → RLS
SCADA EMS Gateway ──HTTPS (исх.)──►  │
  └─ Modbus TCP в локальной сети     ▼
Приборы HTTP push ──HTTPS────────► PostgreSQL ◄── scripts/worker.ts
                                                   (правила, напоминания, почта, обслуживание)
```

Модули `ems-app/lib`:

- `domain/` — чистые функции без БД: обработка показаний, распределение по корзинам, тарифы, прогноз, обязательства, аномалии, планы подписки, протоколы. Покрыты юнит-тестами.
- `services/` — работа с БД: приём показаний, агрегаты, аналитика, стоимость, финансы, панели, события, уведомления, почта, монитор правил, шлюзы, токены, подписки, демо.
- `server/` — HTTP-слой: аутентификация, выбор организации, RBAC, CSRF, лимиты, валидация.

Иерархия: Организация → Объект (`ems_sites`) → узлы произвольной глубины (`ems_nodes`: здание, зона, линия, шкаф, узел учёта) → Прибор → Канал. Для Home узлы не используются — прибор привязан к объекту.

Сущности: организации, пользователи, членства, приглашения, сессии, объекты, узлы, шлюзы, коды регистрации, приборы, каналы, история коэффициентов, показания, журнал исправлений, конфликты повторной доставки, часовые и суточные агрегаты, выпуск продукции, задания шлюза, журнал подключения, токены приборов и API, поставщики, лицевые счета, тарифы, начисления, обязательства, оплаты, получатели уведомлений, правила, события, очередь писем, мобильная лента, планы, подписки и их история, счётчики использования, каталог, заявки на оборудование, журнал действий.

Технические показания (`ems_readings`) и финансы (`ems_charges`, `ems_obligations`, `ems_payments`) разделены: расчёт стоимости читает только агрегаты и тарифы.

## 3. Изоляция организаций

- Все таблицы с данными клиентов содержат `org_id` и закрыты политикой RLS `tenant_isolation` (`FORCE ROW LEVEL SECURITY`).
- Обработчик API открывает транзакцию `withOrg(orgId)` (`SET LOCAL ems.org_id`). Даже запрос без фильтра по `org_id` видит только свою организацию.
- Межорганизационный доступ — только `withSystem()` (вход, фоновые задачи); каждая задача по организации выполняется в своей транзакции `withOrg`.
- Организация в запросе (`X-EMS-Org`) проверяется по членству; подмена даёт 403.
- Шлюз пишет только в каналы своих приборов; токен прибора — только в свои каналы.
- **Эксплуатация**: роль приложения не должна быть суперпользователем и не должна иметь `BYPASSRLS` (суперпользователь игнорирует RLS). Создание секций выполняется функцией `SECURITY DEFINER`, роли приложения DDL не нужен. Пример ролей — `tests/helpers/db.ts`.

Проверено: `tests/db/isolation.test.ts` (под ролью без привилегий) и сквозной тест `tests/e2e/flow.test.ts`.

## 4. Аутентификация и права

- Вход: `/api/auth/scada-id/start` → SCADA ID (PKCE, state) → `/api/auth/scada-id/callback` → `userinfo` + `permissions/resolve?application=scada-ems`.
- Роль в корпоративной организации берётся из гранта `scada-ems` и обновляется при каждом входе: `god/admin → admin`, `operator → engineer`, `viewer → viewer`, `none` — доступа нет. `is_super_admin/is_god` → администратор платформы (`/admin`).
- Личное пространство (Home) создаётся каждому пользователю SCADA ID (`EMS_PERSONAL_ACCOUNTS=0` отключает). **Требует подтверждения владельцами SCADA ID**: допускается ли самостоятельная регистрация домашних клиентов без гранта.
- Приглашения по email принимаются при входе через SCADA ID с тем же адресом.
- Роли EMS: владелец, администратор, инженер (приборы, шлюзы, показания, правила), бухгалтер (тарифы, платежи), наблюдатель. Просмотр и администрирование приборов разделены.
- Сессии: веб 12 ч, мобильная 30 дней; список и завершение в «Настройки». Cookie `HttpOnly`, `SameSite=Lax`, `Secure` в production; изменяющие запросы с cookie проверяют `Origin`.
- Режим разработчика `EMS_DEV_LOGIN=1` работает только вне production-сборки.

## 5. Телеметрия

Ключ показания — `(channel_id, measured_at)`: повторная доставка идемпотентна, другое значение на то же время записывается в `ems_reading_conflicts`.

| Ситуация | Обработка |
|---|---|
| Первое показание | Точка отсчёта, расхода нет |
| Обычное | Расход = разность нормализованных значений (`raw × k + смещение`) |
| Опоздавшее | Встраивается в историю; соседние интервалы и агрегаты пересчитываются |
| Отрицательное приращение | Сохраняется как `bad`, в расход не идёт, событие качества |
| Переполнение регистра | По модулю регистра (`rollover_at`) |
| Сброс счётчика | Новая точка отсчёта, расход интервала — неизвестен (не выдумывается) |
| Неправдоподобный рост | `suspect` + событие; если следующее показание вернулось к прежнему уровню — выброс отклоняется автоматически с записью в журнал |
| Часы устройства спешат | Берётся время приёма, флаг `clock_ahead` |
| Раньше установки / старше 5 лет / не число | Отклоняется |
| Смена коэффициента | История коэффициентов; с граничным показанием расход точный, без него — неизвестен |
| Замена прибора | Финальное показание старого + начальное нового; расход не теряется и не задваивается |
| Пропуски | Остаются пропусками; длинный интервал между показаниями распределяется по времени и помечается `allocated` (штриховка на графиках) |

Ручные исправления (отклонить, подтвердить, изменить) пишутся в `ems_reading_corrections` с причиной и автором; исходные значения не удаляются.

Хранение: `ems_readings` и `ems_agg_hourly` секционированы по месяцам (секции создаются при приёме и задачей обслуживания на 3 месяца вперёд), `ems_agg_daily` — по локальным суткам объекта. Графики выбирают разрешение по длине периода: до 2 суток — часы, до 120 дней — сутки, дольше — месяцы. Сырые точки — только по одному каналу и не больше 7 суток. TimescaleDB, Kafka и т.п. не добавлялись.

## 6. Протоколы и шлюз

| Протокол | Статус | Как |
|---|---|---|
| Ручной ввод | реализован | веб, мобильный API |
| Modbus TCP | реализован, испытан на симуляторе | SCADA EMS Gateway; функции 03/04; uint16/int16/uint32/int32/float32/uint64; порядок ABCD/CDAB/BADC/DCBA |
| Modbus RTU | через преобразователь RS-485 ↔ Modbus TCP | прямой опрос RS-485 агентом не реализован |
| Импульсы | через импульсный модуль Modbus | вес импульса = коэффициент, переполнение учитывается |
| HTTP REST (push) | реализован | `POST /api/ingest/v1/readings`, `X-Device-Token` |
| MQTT | спроектирован, **не реализован** | см. ниже |
| OPC UA, M-Bus | **не реализованы** | помечены в каталоге как «в планах» |

На реальных приборах адаптеры не испытывались; карты регистров Eastron SDM120/SDM630 в каталоге взяты из документации производителя и помечены «профиль не испытан».

SCADA EMS Gateway (`ems-gateway/`):

- регистрация одноразовым кодом (24 ч); повторное использование отклоняется и создаёт событие безопасности;
- секрет хранится в облаке как HMAC; ротация агентом раз в 30 дней и отзыв администратором;
- только исходящий HTTPS (http — лишь с явным флагом для отладки); облако к приборам не подключается;
- опрос → запись в буфер на диск с `fsync` → отправка пакетами до 1000 → удаление только после 200;
- буфер по умолчанию 200 МБ; при переполнении удаляются самые старые данные с явным счётчиком `droppedItems` (виден в карточке шлюза);
- экспоненциальная пауза при недоступности облака (2 с … 5 мин), переподключение к приборам;
- задания диагностики (long-poll): мастер подключения проверяет связь и регистры через шлюз;
- функций записи Modbus нет: управление исполнительными механизмами не реализовано намеренно;
- systemd-служба от отдельного пользователя `scada-ems` (`scada-ems-gateway.service`).

MQTT (проект): брокер с TLS, пользователь на устройство (логин = id прибора, пароль = токен прибора), ACL `ems/{org}/{meter}/up/#` только на публикацию своего топика, QoS 1, полезная нагрузка как у HTTP push, идемпотентность по `(channel, measured_at)`, мост брокер → `ingestReadings`.

## 7. Тарифы и стоимость

Расчётный модуль не зависит от сбора показаний (`lib/domain/tariffs.ts`). Встроенных «актуальных» цен нет — тарифы вводит пользователь или администратор, с историей и датами действия (новый бессрочный тариф закрывает прежний).

- Электроэнергия: одноставочный, зонный (2–4 зоны, интервалы проверяются на покрытие суток без пересечений). Зоны берутся из регистров Т1/Т2/Т3 прибора, иначе — из почасовых данных; без них сумма не считается, а не обнуляется.
- Промышленные составляющие задаются явно по договору: заявленная мощность или среднее/максимум по рабочим дням в часы пиковой нагрузки; дополнительные начисления.
- ГВС одно- и двухкомпонентная, водоотведение по сумме ХВС+ГВС или своему прибору, фиксированные услуги.
- Каждая сумма подписана источником: «по квитанции» (`ems_charges.source=actual`), «расчёт по показаниям», «прогноз».
- Прогноз: факт + среднесуточный расход за последние 14 дней с данными × оставшиеся дни; текущие неполные сутки в среднее не входят; уверенность «надёжный / приблизительный / грубый».

## 8. Платежи и уведомления

- Обязательства: срок оплаты, отдельный срок передачи показаний, повторение (ежемесячно / раз в N месяцев / ежегодно), сумма фиксированная, по расчёту или вручную, получатели, примечание.
- Статусы «ожидается / скоро срок / просрочено / оплачено» вычисляются. Оплата — только ручная отметка пользователя; после неё создаётся следующее обязательство серии.
- Напоминания: об оплате (за N дней), о передаче показаний, о просрочке — каждое один раз на срок (`ems_reminders_sent`), в час, выбранный получателем.
- Адреса подтверждаются одноразовой ссылкой (48 ч, хранится хэш, подтверждение POST-запросом со страницы, чтобы ссылку не «нажимали» почтовые сканеры). Для каждого адреса — типы уведомлений, объекты, час, пауза.
- Очередь `ems_notifications`: причина, получатель, ссылка на объект, статус, попытки, ошибка. Повторы через 1, 5, 15, 60, 180 мин; восстановление «зависших» после сбоя; лимит писем по тарифу.
- События: одно открытое событие на ключ (повторы увеличивают счётчик, письмо не дублируется), уровни важности, окна времени, повтор письма по правилу, подтверждение и закрытие с комментарием, автозакрытие при исчезновении условия.
- Правила: потеря связи, превышение мощности, превышение расхода, непрерывный расход (утечка), ночное потребление, рост к сопоставимому периоду, прогноз выше бюджета, месячный лимит. Выводы о непрерывности и ночном расходе делаются только по измеренным, а не распределённым часам.
- Мобильная лента `ems_feed` + `pg_notify`.

## 9. API

REST, JSON, ошибки `{error, code, details}`. Аутентификация: cookie сессии, `Authorization: Bearer ems1.…` (мобильный клиент), `Bearer emsk_…` (интеграции, разрешения `read`, `readings:write`, `production:write`), `Gateway <id>:<secret>`, `X-Device-Token`.

- `/api/auth/*` — вход SCADA ID, `me`, выход, сессии, смена организации.
- `/api/v1/*` — организация и пользователи, объекты и узлы, приборы (создание, замена, вывод, токен, диагностика), коэффициенты, показания и исправления, ряды, сравнения, тепловая карта, экспорт CSV, панели Home/Industrial, состояние оборудования, лицевые счета, тарифы, начисления, стоимость, калькулятор, обязательства и оплата, события, правила, адреса уведомлений, журнал писем, шлюзы и задания, API-токены, выпуск продукции, подписка, каталог и заявки, демо, первый запуск.
- `/api/mobile/v1/*` — обмен токена SCADA ID, сводка, лента (long-poll).
- `/api/gateway/v1/*` — регистрация, конфигурация, пакеты показаний, heartbeat, задания, журнал, ротация секрета.
- `/api/ingest/v1/readings` — HTTP push приборов.
- `/api/admin/*` — администрирование платформы.

## 10. Подписки SCADA EMS

Цены и лимиты — в таблице `ems_plans`, меняются в `/admin`. Начальные значения:

| План | Цена | Объекты | Приборы | Шлюзы | Польз. | Писем/мес | Детальная история | Мин. опрос |
|---|---|---|---|---|---|---|---|---|
| Home Базовый | 199 ₽ | 1 | 6 | 1 | 2 | 60 | 90 дней | 15 мин |
| Home Plus | 349 ₽ | 3 | 15 | 2 | 5 | 200 | 400 дней | 5 мин |
| Industrial Start / Pro / Enterprise | по договору | 1 / 10 / ∞ | 50 / 500 / ∞ | 3 / 30 / ∞ | 10 / 50 / ∞ | 2 000 / 20 000 / ∞ | 400 / 730 / 1825 | 60 / 10 / 5 с |

Пробный период 30 дней. Лимиты проверяются при создании (402 с понятным текстом), предупреждение при 80%. После окончания периода: 30 дней льготного приёма данных, затем изменения и приём приостанавливаются, **история не удаляется** и доступна для просмотра. Онлайн-оплаты нет (провайдер не утверждён): заявка на тариф фиксируется в истории и активируется администратором. Оборудование оплачивается отдельно.

Экономика Home по результатам нагрузочного теста — в разделе 12.

## 11. Каталог оборудования

`ems_catalog_models`: производитель, модель, ресурс, протоколы, требуемый шлюз или адаптер, питание, передача, инструкция, статус совместимости (`verified`, `profile_untested`, `manual_only`, `planned`). Для приборов без интерфейса явно сказано, что нужен импульсный модуль или шлюз. «Заказ» — заявка на подбор (`ems_device_requests`), обрабатывается в `/admin`; онлайн-покупки нет. Регистрация оборудования по QR не реализована: в каталоге нет модели с безопасной первичной привязкой.


Тестам нужна PostgreSQL с суперпользователем для создания временных баз (`EMS_TEST_ADMIN_URL`, по умолчанию `postgres://ems:ems@127.0.0.1:5432/postgres`).

Визуальная проверка: Playwright, 47 страниц на 1440 px и 375 px — без горизонтального переполнения и ошибок в консоли.

Нагрузочный тест: `node scripts/load-test.ts <каналов> <показаний на канал> <пакет>` — результаты ниже.

Прогон на стенде разработки (4 vCPU, PostgreSQL 16 на той же машине, без настройки): 200 каналов × 2 880 показаний (30 суток раз в 15 мин) = 576 000 показаний, пакеты по 500, тот же сервис `ingestReadings`, что вызывают API и шлюзы.

| Показатель | Результат |
|---|---|
| Приём | 7 955 показаний/с (72 с на 576 000); пакет p50 59 мс, p95 85 мс, max 111 мс |
| Повторная доставка 50 показаний | 17 мс, все `duplicate`; другое значение на то же время — `conflict` |
| Сверка | сумма расхода по показаниям = по часовым = по суточным агрегатам (574 726,165) |
| График: 1 канал, месяц по суткам / неделя по часам | 1 мс / 2 мс (медиана) |
| График: 200 каналов, месяц по суткам / 2 суток по часам | 5 мс / 12 мс |
| Хранение | показания 194 байта/шт. (106,6 МБ), часовые агрегаты 39,1 МБ, суточные 3,4 МБ |

Первая версия приёма пересчитывала агрегаты отдельно для каждого канала каждого пакета (около 9 запросов на канал) и давала ~310 показаний/с. Теперь типовой поток — новые показания после последнего сохранённого — идёт быстрым путём: оценка в памяти, одна массовая вставка, приращение часовых и суточных агрегатов `INSERT … ON CONFLICT`, одно обновление каналов (фиксированное число запросов на пакет). Опоздавшие и повторные показания, ручной ввод и автоматическое отклонение выбросов по-прежнему идут полным путём с повторной оценкой соседей и пересчётом агрегатов. Строки каналов блокируются на время пакета в порядке `channel_id`, поэтому одновременная доставка в один канал не портит приращения. Совпадение быстрого пути с полным пересчётом (включая обрывы, переход через сутки, сброс счётчика и мгновенные величины) проверяется тестом `tests/db/ingest.test.ts`.

Что это значит для Home: прибор с опросом раз в 15 минут — ~6,5 МБ показаний и ~2,4 МБ часовых агрегатов в год (около 9 МБ); квартира с 4 приборами — около 36 МБ в год, при ручном вводе раз в месяц — килобайты. Нагрузка приёма от такого объекта — тысячные доли показания в секунду, поэтому при цене 199–349 ₽/мес основная статья затрат — хранение и резервные копии, а не вычисления; физическое удаление детальной истории по сроку тарифа (раздел 14) — первое, что стоит включить при росте числа объектов. Цифры получены на одной машине и не заменяют проверку на целевом сервере.

## 13. Запуск

Переменные окружения (`ems-app/.env.example`): `EMS_DATABASE_URL`, `EMS_AUTH_SECRET` (≥ 32 символов), `EMS_PUBLIC_URL`, `SCADA_ID_ISSUER`, `SCADA_ID_API`, `SCADA_ID_CLIENT_ID`, `SCADA_ID_CLIENT_SECRET`, `SCADA_ID_APPLICATION`, `EMS_MAIL_PROVIDER` (`helper` | `file` | `none`), `WMS_SEND_MAIL_BIN`.

```bash
cd ems-app
npm ci
node scripts/migrate.ts          # ролью-владельцем схемы
npm run build
npm start                        # роль приложения без суперпользователя
node scripts/worker.ts           # отдельная служба
```

Перед выкладкой: зарегистрировать клиента `ems` в realm `scada-system-id` с redirect `https://<домен>/api/auth/scada-id/callback`, завести приложение `scada-ems` в сервисе прав SCADA ID, настроить nginx (TLS, общий лимит запросов). На сервер EMS не выкладывался.

## 14. Чего нет в этом срезе

- Испытаний с реальными SCADA ID, SCADA Mobile, почтовым помощником и приборами — нет доступа; контракты проверены на тестовых двойниках.
- MQTT, OPC UA, M-Bus, прямой Modbus RTU — не реализованы.
- WebSocket для оперативных значений: панели обновляются запросом, мобильная лента — long-poll.
- Онлайн-оплата подписки и оборудования, регистрация приборов по QR.
- Физическое удаление сырых показаний по сроку хранения тарифа не выполняется (ограничение действует на запросы детальной истории).
- Сравнение со «своим» днём недели в отклонении суток (сейчас — среднее за 7 суток).
- Управление исполнительными механизмами — исключено до отдельного проекта безопасности.
