# Заказы кодов маркировки: документ заказа и погрешность печати

Страница: **Маркировка → Заказы кодов** (`/marking/label-orders`).
Приложение: `/opt/scadatable-wms/current/Frontend`, служба `scadatable-wms-ui`
(Next.js, порт 3004, nginx → `scada25.ru`).
Эта же инструкция короткой версией доступна на странице по кнопке с книжкой.

## 1. Что где живёт

| Данные | Где хранятся | Кто пишет |
| --- | --- | --- |
| Очередь заказов (GTIN, количество, статус, КМ) | sqlite сайдкара `/opt/scada25-print-queue/queue.db`, таблица `code_orders` | планшет у принтера и WMS |
| Документ заказа (номер, автор, источник, план погрешности) | PostgreSQL `wms_label_order_docs` | WMS |
| История заказа (создан, подписан, напечатан, приёмка) | PostgreSQL `wms_label_order_events` | WMS |
| Корректировки факта печати | PostgreSQL `wms_label_order_adjustments` | WMS |
| Настройки погрешности склада | PostgreSQL `wms_app_settings`, ключ `label_order_waste` | WMS |
| Реквизиты СУЗ (omsId, clientToken, сертификат) | localStorage браузера, ключ `wms.labelSuz.settings.v1` | рабочее место |

Очередь и документы связаны по `orderId` (uuid заказа в сайдкаре). Сайдкар ничего
не знает про пользователей WMS, поэтому «кто и откуда заказал» пишется только в базу
WMS. Если база недоступна, страница всё равно показывает очередь — без номеров и факта.

## 2. Документ заказа

Номер: `ZK-ГГММДД-NN` (сквозной внутри дня и склада), выдаётся при создании.

Поля документа:

- `created_at` — когда заказан;
- `author_login`, `author_fio`, `author_position` — кто заказал (берётся **из сессии WMS**,
  а не из тела запроса: подписаться чужим именем через API нельзя);
- `origin` — `wms-ui` или `printer-terminal`;
- `origin_detail` — откуда: для WMS «интерфейс WMS · Chrome · IP 10.х.х.х», для планшета — номер ТСД;
- `gtin`, `item_code`, `nomenclature_name`, `sticker_type`, `quantity`;
- `planned_waste_qty`, `waste_percent` — план погрешности **на момент создания заказа**
  (позднее изменение настроек старые документы не переписывает);
- `comment` — комментарий оператора;
- `payload_json` — служебное: сколько кодов реально требовалось (`neededQty`),
  плановый расход этикетки (`labelsQty`), флаг «запас в заказ».

Заказы, пришедшие с планшета, и заказы, созданные до внедрения документов, получают
документ автоматически при первом чтении списка (`backfillLabelOrderDocs`): автор пустой,
источник — терминал печати, в `payload_json` стоит `backfilled: true`.

История (`wms_label_order_events`) пишется на каждом шаге:
`created`, `codes_ready`, `status`, `printed`, `receiving`, `adjustment`,
`adjustment_reverted`, `deleted`. В каждом событии — автор, источник и текстовое описание.

## 3. Погрешность печати

Печать идёт с первой этикетки, но рулон приходится проматывать, и в конце остаётся
хвост пустых этикеток. Эти этикетки со склада ушли, а кодов на них нет — без учёта
хвоста остаток расходника всегда врёт.

Настройки (шестерёнка → «Погрешность печати», таблица `wms_app_settings`,
ключ `label_order_waste`):

| Параметр | Смысл | По умолчанию |
| --- | --- | --- |
| `wastePercent` | плановый хвост, % от количества кодов | 3 |
| `minWasteQty` | минимальный хвост в штуках | 0 |
| `addWasteToOrder` | заказывать `N + хвост`, чтобы годных было ровно `N` | выкл. |
| `roundTo` | кратность количества (рулон, блок), 0 — не округлять | 0 |
| `alertPercent` | расхождение факта с планом в п.п., после которого строка краснеет | 5 |
| `requireFactAfterPrint` | помечать напечатанные заказы без корректировки | вкл. |

Формулы (`lib/wms/label-order-waste.ts`, один и тот же код на сервере и в браузере):

```
хвост          = max(ceil(количество × wastePercent / 100), minWasteQty)
заказ кодов    = addWasteToOrder ? roundUp(количество + хвост, roundTo) : roundUp(количество, roundTo)
расход этикетки = заказ кодов + хвост        // при addWasteToOrder хвост уже внутри заказа
```

Диалог «Новый заказ» показывает все три числа сразу и предупреждает, если на складе
расходника меньше, чем плановый расход этикетки (материал берётся из номенклатуры
с признаком «Расходник для печати стикеров», подбор — по виду стикера).

## 4. Корректировка факта

Пример из жизни: напечатали 100 годных этикеток и ещё 30 просто промотали.
Кнопка «Внести факт» (или «Факт печати» в меню строки) → окно документа, вкладка
«Факт печати». Три поля:

- **напечатано годных** — этикетки с кодом, ушедшие на продукцию;
- **промотано вхолостую** — пустой хвост и прокрутка;
- **брак** — испорченные при печати.

Считается:

```
расход по факту = годные + промотано + брак
погрешность, %  = (промотано + брак) / годные × 100
расхождение     = погрешность факта − погрешность плана (в п.п.)
```

Корректировок может быть несколько (печать в несколько заходов) — суммы складываются.
Ошибочную запись можно отменить: она остаётся в журнале с `reverted_at`/`reverted_by`
и перестаёт попадать в сумму. Кнопка «По плану» подставляет плановые цифры заказа.

В списке колонка «Факт печати» показывает `годные + потери`, процент погрешности и
вердикт: «в пределах плана», «выше плана на X п.п.», «перерасход», «не напечатано N из
заказа». Фильтр «Нужен факт» собирает напечатанные заказы без корректировки.

## 5. API

Все маршруты — `runtime = nodejs`, `dynamic = force-dynamic`.

```
GET  /api/wms/label-code-orders?limit=100&siteCode=DEFAULT
     → { orders: [{ …заказ, doc, fact }], settings }   # + автосоздание документов для старых заказов

GET  /api/wms/label-code-orders/{id}?doc=1&siteCode=DEFAULT
     → { order, doc, fact, adjustments, events, settings }
GET  /api/wms/label-code-orders/{id}?download=1        # codes.txt

GET  /api/wms/label-code-orders/nomenclature?query=…   # позиции с GTIN + дата последнего заказа

POST /api/wms/label-code-orders
     { action: "create",  gtin, quantity, nomenclatureName, itemCode, stickerType,
       wastePercent?, addWasteToOrder?, comment? }     → { order, doc, plan }
     { action: "adjust",  id, printedQty, spooledQty, defectQty, comment? }
                                                       → { fact, adjustments, events }
     { action: "revert-adjustment", adjustmentId }
     { action: "save-settings", settings: {…} }        → { settings }
     { action: "patch",   id, codes?, status?, note? } # прикрепить КМ / сменить статус
     { action: "print",   id, autoStart }              # в очередь печати + в приёмку
     { action: "to-receiving", id }                    # повторно показать коды в приёмке
     { action: "unlock-delete", masterCode }
     { action: "delete",  id, masterCode }
```

Автор для `create`, `adjust`, `print`, `delete` берётся из сессии
(`lib/wms/label-order-author.ts`: cookie `wms_session` или `Authorization: Bearer`).
Мастер-код удаления — `WMS_LABEL_ORDER_MASTER_CODE` в `.env.local` (по умолчанию `223122`).

## 7. Проверка после обновления

```bash
# заказы с документами и настройками
curl -s 'http://127.0.0.1:3004/api/wms/label-code-orders?limit=3&siteCode=DEFAULT' | head -c 800

# что можно заказать
curl -s 'http://127.0.0.1:3004/api/wms/label-code-orders/nomenclature?siteCode=DEFAULT&query=славда' | head -c 500

# журналы в базе
psql "$DATABASE_URL" -c 'select doc_no, author_fio, origin, quantity, planned_waste_qty from wms_label_order_docs order by created_at desc limit 5'
psql "$DATABASE_URL" -c 'select order_id, printed_qty, spooled_qty, defect_qty, author_fio from wms_label_order_adjustments order by created_at desc limit 5'
```

Ничего из перечисленного не удаляет и не меняет коды маркировки: корректировка —
только учёт расхода этикетки, КМ живут в сайдкаре и в приёмке.
